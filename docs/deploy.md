# Deploying Cortex

Three pieces: **Neon** for Postgres, **Render** for the Go API, **Vercel** for the
frontend. Roughly 30 minutes the first time, most of it spent in consoles rather
than in the terminal.

The order below is not arbitrary. The database has to exist before the API can
start, the API's public URL has to exist before Google OAuth can be configured,
and the frontend needs the API's URL at build time. Doing it in a different
order means going back.

---

## 1. Neon — Postgres with pgvector

Render's free Postgres has no pgvector, and Cortex keeps its vectors, its
relational data and its job queue in one database on purpose. So the database is
Neon.

1. Create a project at https://console.neon.tech
2. Copy the **pooled** connection string. Keep `?sslmode=require`.
3. Enable the extension:
   ```sql
   CREATE EXTENSION IF NOT EXISTS vector;
   ```
4. Apply both migration sets **from your machine**, against Neon:
   ```bash
   cd backend
   goose -dir db/migrations postgres "$NEON_URL" up
   go run ./cmd/rivermigrate --database-url "$NEON_URL"
   ```

Two sets because goose owns the application schema and River owns its own — its
DDL contains enums, `$$`-quoted function bodies and triggers that do not survive
being vendored into goose migrations.

Migrations are a local step, not something the container does at boot. A
container that migrates on startup either crash-loops on a bad migration or
races another instance, and neither is a thing you want to debug remotely. The
cost is that you must remember to run this again after any schema change, before
the deploy that needs it.

## 2. Render — the Go API

The repository has a `Dockerfile` and a `render.yaml` blueprint.

1. **New → Blueprint** at https://dashboard.render.com, point it at the repo.
   Render reads `render.yaml` and creates the `cortex-api` service.
2. Fill in the prompted environment variables.

   These are required — the server refuses to start without them, by design,
   rather than answering questions badly:

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | the Neon pooled string from step 1 |
   | `GOOGLE_OAUTH_CLIENT_ID` / `_SECRET` | the **Web** client, not the Desktop one |
   | `AUTH_ALLOWED_EMAILS` | your address — see the warning below |
   | `LLM_KEY_ENCRYPTION_SECRET` | as local, or a fresh 32-byte value |
   | `DEV_USER_EMAIL` | your address |
   | `API_PUBLIC_URL` | **leave blank until step 3** |

   These are optional, and configure the **demo workspace** — the read-only
   sample data a signed-in user can opt into. Leave them out entirely and the
   deployment is bring-your-own-sources: each user connects their own Jira,
   Notion and Gmail in the app, which is the posture most deployments want.

   | Variable | Value |
   |---|---|
   | `JIRA_BASE_URL` `JIRA_EMAIL` `JIRA_API_TOKEN` `JIRA_PROJECTS` | as in your local `.env` (all four, or none) |
   | `NOTION_TOKEN` | as local |
   | `GMAIL_QUERY_SCOPE` | as local — pins every demo search to the demo slice |
   | `OPENAI_API_KEY` | your key — funds indexing the demo corpus. Required only with a demo workspace; user questions run on each user's own key |

   > **If you configure a demo workspace, set `AUTH_ALLOWED_EMAILS`.** The demo
   > is somebody's real Jira site and real mailbox, scoped by the pins but real.
   > With sign-in open to any Google account, everyone who signs in can query
   > it. The server logs a warning at startup when it sees both, and the startup
   > line always states which workspace — if any — the deployment offers.

   `AUTH_API_TOKEN` is generated by Render. You do not need to know its value
   unless you intend to call the API from a script.

3. Deploy once and let it fail. You need the hostname Render assigns before you
   can finish configuring, which is the one genuinely awkward part of this.
   Take the URL — `https://cortex-api-xxxx.onrender.com` — and set:
   - `API_PUBLIC_URL` to exactly that, no trailing slash
   - `FRONTEND_ORIGIN` to your Vercel URL once step 4 gives you one

4. **Demo Gmail only** — skip this step if you are not configuring one.

   The demo mailbox is the one credential the process cannot obtain for itself:
   the OAuth flow needs a human at a browser, and `make gmail-auth` cannot run
   inside a container. Two ways to get the token in:

   **Secret Files** (service → Settings → Secret Files), with these exact
   filenames:
   - `gmail-credentials.json` — the Desktop OAuth client JSON
   - `.gmail-token.json` — produced locally by `make gmail-auth`

   `render.yaml` already points `GMAIL_CREDENTIALS_JSON` and `GMAIL_TOKEN_PATH`
   at `/etc/secrets/`, where Render mounts them. Secret files persist across
   deploys; the mount is read-only, so a refreshed access token cannot be cached
   back — handled and logged as a warning, not an error, costing one token
   refresh per restart and nothing else.

   **Or `GMAIL_TOKEN_JSON`** — paste the contents of `.gmail-token.json` into
   that environment variable instead of uploading the second secret file. Same
   effect, one less moving part, and it is the option to use on a host with no
   secret-file feature and no persistent disk. The file wins when both are
   present, so this never overrides a local `make gmail-auth`.

   A future alternative, deliberately not built: storing the demo token in the
   database under `LLM_KEY_ENCRYPTION_SECRET`, where every *user's* Gmail token
   already lives. It is the more consistent end state and worth doing if the
   demo mailbox becomes long-lived — but it needs a migration, a seeding path
   and refresh-in-place, for a single optional mailbox.

5. Redeploy. `/healthz` should return 200.

### Why `API_PUBLIC_URL` is not optional

Two independent things break without it, and neither failure names itself:

- **Host-header allowlist.** The API only answers to hostnames it knows, which
  is what closes DNS rebinding. Unset, a deployment answers **421** to
  everything — including Render's health check, so the deploy never goes live
  and the logs look like a service that never started.
- **OAuth redirect URIs.** They are built from this value. Unset, they point at
  `http://localhost:8080`, so signing in on a public site sends the browser to
  the user's own machine.

The startup log warns when the server is bound beyond loopback with this unset.
If a deploy is failing its health check, read that line first.

## 3. Google OAuth

In https://console.cloud.google.com/apis/credentials, on the **Web** client:

**Authorized redirect URIs** — add both, exactly:
```
https://<your-render-host>/api/auth/google/callback
https://<your-render-host>/api/connections/gmail/callback
```

**Authorized JavaScript origins** — add your Vercel origin:
```
https://<your-vercel-app>.vercel.app
```

Keep the localhost entries alongside these so local development keeps working:
```
http://localhost:8080/api/auth/google/callback
http://localhost:8080/api/connections/gmail/callback
```

Google matches these as exact strings. `http` vs `https`, a trailing slash,
`127.0.0.1` instead of `localhost`, or the frontend's port instead of the API's
all produce the same `redirect_uri_mismatch`. Changes take a minute or two to
propagate, so a retry that fails immediately is not evidence you got it wrong.

Also check the **consent screen**: while the app is in Testing, every address
that signs in must be listed under Test users. And the `gmail.send` scope is
restricted — it must be on the client, or the write-enable consent completes and
grants nothing, and Cortex correctly refuses to turn writes on.

---

## 4. Vercel — the frontend

1. **New Project**, same repo, set **Root Directory** to `frontend`.
2. Environment variable: `NEXT_PUBLIC_API_URL` = your Render URL.
3. Deploy, then go back and set Render's `FRONTEND_ORIGIN` to the Vercel URL and
   redeploy the API. Both halves need to know about each other, which is why
   this is the step that gets forgotten.

---

## 5. Check it

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://<render-host>/healthz     # 200
curl -s -o /dev/null -w '%{http_code}\n' -H 'Host: nope.example.com' \
     https://<render-host>/healthz                                        # 421
```

The second one returning 421 is the rebinding guard working. If the first also
returns 421, `API_PUBLIC_URL` does not match the host you are calling.

Then in a browser: sign in, connect a source, ask a question. For write actions,
enable writes per source first — Gmail will send you through a fresh consent
screen for the send scope.

## Things worth knowing

**The free tier sleeps.** Render's free instance spins down when idle and takes
a few seconds to wake. That matters more here than for a normal API: the River
workers stop with the instance, so a run paused awaiting approval does not
resume until something wakes the service. An hourly sweep releases anything
left behind, but for a live demo, wake the service first and keep a tab open.

**Seeding runs from your machine**, not from the deployment: `make seed` against
the Neon URL. The seeder writes to real Jira, Notion and Gmail, so run it once
and deliberately.

**Write actions send real email.** `GMAIL_SEND_ALLOWED_DOMAINS` is empty by
default, which permits any recipient domain. On anything public, set it.

**Rotating `LLM_KEY_ENCRYPTION_SECRET` invalidates every stored LLM key** —
users re-enter theirs. If you want the local and deployed databases to be
interchangeable, use the same secret for both.
